## Observations

- **Parallel fixers worked well** when themes were file-disjoint, but every parallel batch required at least one rebase as PRs squash-merged out from under each other. Worktree isolation (`isolation: "worktree"`) prevented filesystem races between agents — strongly recommended for any parallel batch >2.
- **Required CI checks (`CI / Lint`, `CI / Build`, `CI / Test`) only register when the PR targets `main`** — `.github/workflows/ci.yml` triggers on `pull_request` with `branches: [main, master]`. The skill's "PR targets working branch" model doesn't fit this repo. Last run noticed this implicitly; this run made it explicit. The `gh pr edit --base main` retarget alone does NOT register the workflow — must close+reopen the PR or push a new commit. **Going forward: target `main` directly from the start.**
- **Squash-merging from a parallel batch creates rebase storms.** When 5 PRs all merged within a few seconds, each subsequent merge required the next PR to rebase on the new tip. The cumulative time spent rebasing was non-trivial (~2 min per cycle for the rebase + force-push + new CI). Suggest: either (a) cap parallel batches at 3 to bound rebase pressure, or (b) accept the rebase cost as the price of throughput.
- **Locked worktrees prevent merge-cleanup of local branches.** `gh pr merge --delete-branch` on a branch held by a still-running worktree fails the local delete (remote delete still succeeds). Cosmetic only, but the cleanup step at end-of-run needs to handle locked worktrees explicitly.
- **The pr_count is awkwardly tracked.** Two failed merges in this run caused me to over-decrement. Recommend: instead of a counter, query `gh pr list --state merged --search 'head:overnight/<RUN_ID>/'` at the top of each loop iteration.
