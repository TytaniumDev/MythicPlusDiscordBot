## Observations

1. **PR target = `main` directly** (per last run's lesson). Worked. CI registered correctly when PRs targeted main from creation. The skill's "target working branch" pattern is wrong for this repo — `.github/workflows/ci.yml` only triggers on PRs targeting main.

2. **`gh pr merge --admin` to bypass "up-to-date" branch protection** worked for branches with no actual file conflicts but stale base. No conflicts arose this run thanks to file-disjoint batching.

3. **Worktree timing pitfall:** PR #533 (parseSeasonPairs) was authored in a worktree branched off `main` early in the run, then sat unmerged while several sibling PRs landed that touched the same files (`firestoreService.ts:107`, `firebaseService.ts` import block). When CI was about to run, the branch was actually conflicting — `gh pr update-branch` reported "Cannot update PR branch due to conflicts" rather than rebasing. Closed it; redid the change directly on a fresh branch from latest main as PR #540. **Lesson:** `gh pr update-branch` is unreliable on conflicting branches; close+redo is faster than retry-loop. Future runs: a worktree's `git pull origin main` should run RIGHT BEFORE pushing, not at agent start.

4. **`gh pr checks <N>` shows "no checks reported" silently when CI didn't trigger.** This happened on #533 even after close+reopen + empty-commit-push retrigger. Likely the conflict state caused GitHub to skip the workflow run. Worth distinguishing from genuinely-pending CI in future orchestrators.

5. **Orchestrator CWD leakage across Bash tool calls.** `cd $WT` to push an empty commit (in the parseSeasonPairs retrigger flow) silently changed the orchestrator's CWD; subsequent `git status` / `git checkout main` calls operated on the worktree, not the main repo. Future runs should `cd /repo-root` defensively before each git command — or use `git -C <path>` explicitly.

6. **`package.json` edits "leaked" into the main repo state on two occasions** even though the dep-bump fixer ran in its own worktree. Most likely cause: `npm install` from a worktree updates the SHARED `package-lock.json` in the main repo (since worktrees share git tree but workspaces share lockfile). The shared lockfile is the right design for this monorepo, but the side-effect surprised the orchestrator. Documenting it so next run isn't surprised.

7. **T15 (WoWPlayer construction in utils) abandoned on premise verification.** The fixer correctly identified that `WoWPlayer.create` already validates implicitly via intersection with known role-name constants. Recording in style-decisions + avoid-list so future critics don't re-flag this.

8. **No fail/reject/abandon at CI stage.** All 20 shipping PRs passed CI on first try; no fixer needed a CI-fix retry. The deliberation phase + file-disjoint batching kept the merge train clean.
